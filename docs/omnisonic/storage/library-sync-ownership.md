# Library sync ownership and pruning — `library-sync-ownership.md`

Purpose: Pin the server/local column-ownership model, per-album transaction boundaries, resume-point merge rules, and full-sync pruning (tombstones) for the server-to-device library walk.

How derived: the tombstone-pruning decision (full sync only, three confirmed rules — see `../decisions.md`); direct code inspection and test runs in this repository. Evidence categories: own design decision record, own-source reading, in-repository test runs.

Confidence:
- [VERIFIED] Each album (and each entity batch: artists, genres, radios, playlists, bookmarks, pruning, status) commits in its own short transaction; the network fetch (`getAlbum`) runs outside the transaction. A concurrent outbox write completes while a sync is parked waiting on the provider (test: `outbox enqueue completes while the sync waits on the network`).
- [VERIFIED] Column ownership is pinned by `SyncColumnOwnershipTest`: every column of SongEntity/AlbumEntity/ArtistEntity is classified KEY/SERVER/LOCAL; a new column fails the test until classified. Server-owned columns are written by the syncer via DAO `updateServerFields` (INSERT OR IGNORE + UPDATE; no `ON CONFLICT DO UPDATE` — see `sqlite-api29-floor.md` for the API 29 syntax floor) or, for the prune-time tombstone flag, via the dedicated `tombstoneUnseen` query; locally-owned columns are never in the SET list.
- [VERIFIED] Locally-owned song state (playCount, lastPlayed, skipped, userRating, isFavorite, resumeMs, resumeUpdatedAt, replay gain, clips, isAudiobook) and album state (isCompilation, description, resumeTrackPath, isAudiobook, discNamesJson, playback state) survive a full sync unchanged.
- [VERIFIED] `missingOnServer` is sync-owned in both directions (FIX-06): `tombstoneUnseen` sets it to 1 for protected songs a complete walk did not report, and `updateServerFields` clears it (`missingOnServer = 0`) whenever the server reports the song again — a tombstoned song that reappears returns to the library with its play history, rating, resume point and every other local field intact (`SubsonicLibrarySyncerPruneTest`).
- [VERIFIED] Resume merge rule: a server bookmark applies only when the song has no pending `resume_point` outbox row AND `bookmark.updatedAtMs` is non-null and greater than `songs.resumeUpdatedAt` (null resumeUpdatedAt counts as 0). Applying stores the server timestamp in `resumeUpdatedAt`; local resume writes (`setResumePoint`) stamp the local now. A bookmark without a timestamp never overwrites local state.
- [VERIFIED] Full-sync-only mark-and-sweep, stamp-based (FIX-01, D-10): every run mints a unique id (DB-stamp floor + per-instance atomic sequence) and writes it into `lastSeenSyncId` of every song/album/artist/playlist row it writes. Songs unseen on the server (stale or absent stamp) are deleted only if playCount == 0 AND no pending outbox row exists AND none of the D-9 local states (userRating, resumeMs, windowStartMs, windowEndMs) is set; otherwise they are tombstoned with `missingOnServer = true` (favorite status alone does NOT block deletion, per the confirmed rule 3). Albums are deleted when unseen and no song rows remain (tombstoned songs keep their album alive); artists are deleted when unseen and no song_artists/album_artists links remain; playlists are deleted outright when unseen. Diff sync never prunes. Chapters of removed songs and removed albums are deleted with them (chunked, `ChapterDao.deleteBySongIds/deleteByAlbumIds`). Verified at scale: 5,000 songs, 1,000 unseen (a fifth of the library — below the FIX-02 half-guard, so the prune runs) → 4,000 survive stamped, 100 played come back as tombstones, 900 deleted; albums/artists follow their children (`SubsonicLibrarySyncerPruneTest`).
- [VERIFIED] FIX-02 prune safety guards (`SubsonicLibrarySyncer.prune`): the walk records the known song count (`COUNT(*)` over the provider's songs, including NULL-stamp rows) before it starts and collects a seen-set of every song id from successful `getAlbum` calls plus every LISTED album id (album ids join the seen-set before the fetch, so a listed album whose fetch fails still counts as reported). Pruning is skipped — with `prune skipped: <reason>` in `Outcome.message` and the sync-status row — when (a) the seen-set is empty (server reported nothing), (b) the reported SONG count is less than half the known song count (the half-guard counts songs only, apples-to-apples against a song count), or (c) any listed album fetch returned null. A shrunk-but-plausible response (seen ≥ half, no fetch failures) still prunes: 1 of 2 songs vanishing deletes normally. Guards evaluate in that order and the reason names the first hit.
- [VERIFIED] NULL-stamp rows join the unseen set: with the safety guards in place, a NULL stamp (queue-snapshot/playback materialisation via `SongRepository.ensureSong`, rows written outside a full walk, local playlist edits) means "not reported by a complete walk" and prunes/tombstones under the same rules as a stale stamp. A played NULL-stamp row tombstones (keeps `missingOnServer = true`, stamp stays NULL); a plain NULL-stamp row deletes; a NULL-stamp album/artist/playlist with no remaining children deletes. Before the guards existed these rows were untouchable (FIX-01 interim form, `lastSeenSyncId IS NOT NULL AND != :runId`); every prune query cites the guard caller in its KDoc.
- [VERIFIED] Run ids are unique per stamp that may exist in the database: minted as `max(processSequence, MAX(lastSeenSyncId) over the four tables for this provider) + 1`, so process restarts and provider re-adds can never reuse a stored stamp, and repeated runs of one instance stay distinct. [UNKNOWN] Two concurrent full syncs of the same provider instance set have no lease; concurrent runs mint distinct ids but interleave their walks (pre-existing upstream hazard, unchanged scope).
- [VERIFIED] `MediaProvider.getAlbum(externalId): ProviderAlbumDetails` returns album + songs in one fetch; the syncer makes N album requests for N albums plus one album-list page request (asserted in tests). `browseDirectory` remains for directory browsing and the local provider.
- [VERIFIED] latinTitle/sortTitle are computed at sync for songs, albums, and artists via `core-model` TextNormalizer (ICU Any-Latin transliteration when available on Android, otherwise NFD + strip marks on the JVM), with `sortKey` lowercased.
- [VERIFIED] O(n^2) genre/radio/playlist lookups replaced with `(providerId, externalId)` DAO queries.
- [VERIFIED] `songs.resumeUpdatedAt`, `songs.missingOnServer`, and the four `lastSeenSyncId` columns exist from schema v1 (D-11 option B). FIX-15 replaced the discarded pre-release migration chain with one clean v1 baseline containing final column names, provider kinds/endpoints, Wi-Fi/mTLS columns, download ownership, queue snapshots, and per-play history; see `schema-v2.md`. No released database exists.
- [VERIFIED] Provider rows now carry `kind` (`REMOTE_SERVER`/`DEVICE`/`VIRTUAL`); `DEVICE` and `VIRTUAL` load through `ProviderEndpoint.None`, while `REMOTE_SERVER` keeps the primary-block validation. `SongRepository.ensureSong` lets playback/favorites/playlists materialise a minimal song row without overwriting SERVER- or LOCAL-owned columns.
- [VERIFIED] (Upsert contract) No DAO uses `OnConflictStrategy.REPLACE` or `INSERT OR REPLACE`; every upsert goes through a `@Transaction` wrapper that resolves the existing id by natural key (`(providerId, externalId)` for library entities, mediaKey for downloads, sourceKey/offlinePath for offline files, join tuples for link tables, `(providerId, mediaType, externalId, action)` for outbox) before a Room `@Upsert`, and returns the resolved id. `SongRepository.ensureSong` selects the existing row first and fills only null snapshot columns (albumId, displayArtist, imagePath, durationMs) via `copy`, so re-materialisation never changes a song's id or resets local state. Rationale: SQLite REPLACE deletes-then-inserts, which orphans join rows on unique-key hits and would fire the provider cascade triggers if `recursive_triggers` were ever enabled (covered by `UpsertSafetyTest`, including the recursive-triggers-ON worst case). `SongDao.fillSnapshotFields` is retained but unused since the `ensureSong` rework; remove it in a routine cleanup.
- [VERIFIED] Parameterized IN lists are bounded: raw single-batch queries are named `...Chunk` and plain-named `@Transaction` default methods feed them `List.chunked(500)` (`SqlChunking.kt`); `DaoSqlBoundedListTest` scans the DAO sources and rejects any parameterized `IN (:`/`NOT IN (:` outside a `Chunk` method. Robolectric's SDK 34 SQLite raises the variable limit, so the 999-bind crash is enforced structurally, not behaviorally. Covered: song/album delete-by-ids, song_artists/album_artists link deletes, chapter delete-by-song-ids/album-ids (FIX-02), album aggregate recompute, artist aggregate recompute (`DaoChunkedOperationsTest`, 1,200-id lists).
- [VERIFIED] Schema v1 includes the four `lastSeenSyncId` columns (all nullable INTEGER, SERVER-owned). Per D-11 (decision B) no migration chain is shipped: FIX-15 replaced the discarded pre-release migrations with one clean v1 baseline, so file-backed databases from before FIX-15 must be recreated during development. `Migrations.ALL` is empty and the harness seeds v1 and validates the identity path.
- [UNKNOWN] The default value of `PRAGMA recursive_triggers` on real Android devices (Robolectric's in-memory harness reports 1, the file-backed migration harness reports 0). Informational only: the app never sets the pragma, no DAO uses REPLACE, and `MigrationHarnessTest` pins 0 on the file-backed harness.
- [UNKNOWN] Behavior against a live server (real Navidrome) — needs a server; not run.

## Ownership model

[VERIFIED] See `SyncColumnOwnershipTest` for the authoritative classification. In short: everything describing the server's copy (titles, paths, codec facts, counts, timestamps) is SERVER-owned; everything the app or user produces (play history, favorites, ratings, resume points, clips, audiobook flags, editorial text) is LOCAL-owned. `missingOnServer` is the one sync-maintained flag: SERVER-owned (only the syncer writes it) but not part of the server's copy — it records the local view of the server's copy, set by the prune's tombstone pass and cleared by `updateServerFields` when the server reports the song again (FIX-06).

## Run stamps (FIX-01, D-10)

[VERIFIED] `lastSeenSyncId` (INTEGER, nullable) exists on songs, albums, artists, and playlists in the v1 baseline. It is SERVER-owned: only the syncer writes it, via `updateServerFields` / the playlist entity upsert, always with the current run id.

[VERIFIED] Run-id minting (`SubsonicLibrarySyncer.nextRunId`): `max(per-instance atomic sequence, MAX(lastSeenSyncId) across the four tables for this provider) + 1`. The DB floor makes a stored stamp impossible to reuse (process restarts, provider delete/re-add); the sequence keeps repeated or concurrent runs of one instance distinct. Wall-clock time is not involved, so tests are deterministic.

## Pruning rules (FULL sync only, behind the FIX-02 safety guards)

`SubsonicLibrarySyncer.prune` records the known song count before the walk and
collects the seen-set (reported song ids + listed album ids, even when an
album's fetch fails). If the seen-set is empty, the reported song count is
below half the known count, or a listed album fetch failed, NOTHING is pruned
and the outcome message reads `prune skipped: <reason>`.

1. Songs not seen (stale or absent stamp): DELETE when playCount == 0, no outbox row exists for the externalId, and no D-9 local state is set (userRating, resumeMs, windowStartMs, windowEndMs all NULL); otherwise keep and set `missingOnServer = true`. The flag clears again the next time a sync reports the song (`updateServerFields` writes `missingOnServer = 0`, FIX-06).
2. Albums: deleted when not seen and no song rows remain. Tombstoned songs keep their album. Chapters of a removed album go with it.
3. Artists: deleted when not seen and no link rows remain.
4. Playlists: deleted when not seen; orphaned entries cleaned.
5. Diff sync never prunes.
6. **FIX-02 final: rows whose `lastSeenSyncId` is NULL join the unseen set** (`(lastSeenSyncId IS NULL OR lastSeenSyncId != :runId)` in every prune query) — the FIX-02 guards above are what make a NULL stamp safe to interpret as "not reported by a complete walk". Before FIX-02 these rows were untouchable (FIX-01 interim). Every prune query cites the guard caller in its KDoc.

## Authentication failures

[VERIFIED] A `ProviderAuthException` (Subsonic codes 40–44, HTTP 401/403) ends the walk with the normal failed sync-status row and rethrows, but also reports the provider through `onAuthFailed` so `ProviderStatusTracker` marks it `AUTH_FAILED`; the next run-gate check blocks before any read or write. A completed sync calls `onAuthSucceeded`, clearing a stale marker. Generic sync failures record the same failed status and rethrow without touching the auth marker. [VERIFIED by `SubsonicLibrarySyncerTest` — `auth failure marks the provider auth failed and rethrows`, `successful sync clears a prior auth failure`, `generic sync failure does not mark auth failed`.]

## Resume merge

[VERIFIED] Server bookmark wins only if newer than the local resume state and no pending local resume upload exists. This prevents a pending outbox row (newer local data) from being clobbered by an older server bookmark.
