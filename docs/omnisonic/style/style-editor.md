## 1. Session core

[VERIFIED — source] An editing session holds the style id it opened and the `StyleRevision` of the document it last observed. Every write it issues carries that revision. There is no editor-owned file I/O, no second copy of the document on disk and no editor-side merge: a field edit is a `transform` and the coordinator applies it to the document it reads inside its lock.

| Session action | Command | Notes |
|---|---|---|
| Open an existing user style | `update(id, revision, transform)` per committed change | the transform receives the latest committed document, not a snapshot |
| Start editing a built-in | auto-copy, then `update` the copy (§1.5) | persists and activates a pristine fresh-id copy whose D-82 base is the built-in, clears session history, then applies one `update`; the asset is never rewritten or silently shadowed |
| Save a new style | `create(document, baseId)` | refuses an occupied id; the derivation entry is recorded with the write |
| Rename | `rename(id, revision, name)` | name only; identity is the id |
| Reset | `reset(id, revision, scope)` | field, section or all from the derived base; an unknown path is refused |
| Delete | `delete(id)` | the store clears the active pointer when the deleted style was active |
| Apply live | `switch(id)` | the store validates the candidate before writing the pointer; a pointer failure is `Failed` |
| Import | `importWrite(document, baseId)` | collision policy below; never activates |
| Restore | `restoreWrite(document, baseId, activate)` | called after the caller's data restore; activation failure is reported as saved inactive |

### 1.1 The target moved

[VERIFIED — source/test] The editor's revision is the only authority on what it is editing. An external write, delete or restore changes the committed revision; the next command returns `StyleMutationResult.StaleStyle` and leaves the file untouched. The session must then reload the document (or keep editing a detached copy and say so) — it must never retry the same transform against the newer document as if nothing happened, because that is how a queued edit lands on a restore the user did not intend to overwrite. A `NotFound` after a delete ends the session for that id.

### 1.2 Applied, undoable, failed

[VERIFIED — source] Only `Saved`, `Deleted` and `Switched` mean the change landed. `Partial` means the style file was committed but a companion step was not: the session shows the real state (for example "saved, not activated") and may treat the document write as applied, never as fully undone. `Failed`, `Rejected`, `StaleStyle` and `NotFound` change nothing and must not advance any Undo stack. Undo remains session-only (TODO 5d); it is not persistence and does not survive process death. [VERIFIED — source/test, D-113] `Failed` also covers the delete-time pointer **read** failure: the coordinator snapshots the active id before deleting and, when the pointer cannot be read, aborts before any file or derivation deletion — no `Deleted`, no Undo entry, no temp file. A pointer **write** failure after the file is gone stays `Partial` (D-108); ordinary observation of the pointer keeps its default fallback.

### 1.3 Derivation and reset base

[VERIFIED — source] A copied or imported style records the built-in it derives from in `StyleDerivationStore` (D-82). `reset` and a later `duplicate` read that entry; a missing entry logs one warning and uses the default built-in explicitly. This is what keeps reset-all honest after a restart instead of silently restoring the wrong built-in.

### 1.4 Import and restore identity

[VERIFIED — source/test] Both commands run through the same lock and the same D-83 policy: a free id is preserved (so export → import → export stays byte-equal), an identical normalized document is a no-op, a different document on an occupied id — including a built-in id — is saved under a fresh id with a derivation entry. Neither command activates by itself; restore activates only when asked, after the caller's data restore has succeeded, and reports a pointer failure truthfully. The conversion report, SAF flow and backup UI remain TODO 5e.

### 1.5 First edit of a built-in: auto-copy (TODO 5b WP01, D-116 Q6)

[VERIFIED — source/test] A built-in id is refused by every mutating command, so the editor does not ask the user to duplicate first. The first committed edit of a built-in goes through `StyleEditorCommands.commitEdit` (`:feature-settings`): it checks the target revision against the built-in document, generates a unique app-side name (`StyleCopyNaming`, Q8), persists and activates a pristine fresh-id copy whose D-82 derivation base is that built-in through one `create(..., activate = true)`, then clears the route session's Undo history and applies the mutation as one `update` on the copy. The first edit is therefore the first undoable command and Undo never crosses the switch; the built-in asset is never written and no `<built-in id>.json` shadow appears. A duplicate name is resolved app-side (base name plus ` copy`, then ` copy 2`, ` copy 3`, compared case-insensitively), never by asking the user.

[VERIFIED — test] Failures keep the coordinator's typed meaning. A copy write failure is `Failed` with nothing written, no pointer change, no derivation entry and no Undo entry. A switch failure is `Partial` (saved inactive, carrying the committed copy and its revision); the mutation is not applied and not retried, and the pointer write is attempted once. An `update` failure after a successful switch leaves the active pristine copy and records no Undo entry. For an already-custom target the seam issues exactly one `update` and no copy. The session keeps only a count (`record()`/`clear()`); no persistent Undo and no new Undo UI are added here.

## 6. Styles (TODO 5b WP02, D-116 Q9)

[VERIFIED — source] The Styles area (`styleEditor/styles`) is the real list instead of the 5a placeholder. Its state is read-only: entries come from `StyleRepository.list()` in repository order (built-ins first in asset-name order, then user files in file-name order), each with its id and name; the applied style is the resolved active profile's document id and name; and the state carries exactly one preview token set from the live `ObservableStyleTokenSource.tokenFlow` — never one per row. `repository.changes` re-lists after a write or delete (for example the §1.5 auto-copy), so the list needs no manual refresh. The screen writes nothing directly; the only mutation is a pick, which calls `StyleMutationCoordinator.switch(id)`.

[VERIFIED — test] Every valid entry renders once as a labelled `Role.Button` row — "Apply <name>" or, for the applied style, "Apply <name>, currently active" — and the active row is the only one marked: a visible "Active" label, a check icon and the `selected` semantics. Exactly one preview card names the active style and reads the single preview token set. A successful pick repaints the card and the app theme through the existing profile flow with no restart and no manual refresh. A refused candidate (`Rejected`) or a pointer write failure (`Failed`) is kept as a typed `StyleEditorSwitchFailure`; the screen shows "Could not apply <name>." with the coordinator's own detail and "The active style did not change.", and the marker and preview stay on the style the store still applies. A pick in flight is guarded, so a row cannot queue a second switch.

[VERIFIED — source/test] Duplicate is offered on every row, rename and delete only on user-style rows (§7, §8); a damaged user file renders as its own "Needs attention" row with only the safe recovery actions (§8); import is absent (5e). The route keeps the D-114 back chain (Settings → hub → Styles) and the route-scoped session; the shared `StyleEditorViewModel` also injects the repository and the 5a0 coordinator. Damaged files stay out of this list because `StyleRepository.list()` already surfaces only decodable styles; the sealed valid/damaged entry model and the recovery commands are WP04.

## 7. Lifecycle commands (TODO 5b WP03, D-116 Q7/Q8)

[VERIFIED — source] Duplicate and rename are commands on the committed seam (`StyleEditorCommands`, `:feature-settings`), issued by `StyleEditorViewModel` and rendered by the Styles screen. The screen performs no repository write; every mutation still runs through the one 5a0 coordinator, the one mutex and the one set of typed results, and the list re-lists through `repository.changes`.

**Duplicate (Q7).** [VERIFIED — source/test] `StyleEditorCommands.duplicate(id)` reads the source whether it is a built-in or a user style, asks the coordinator for the source's D-82 derivation base through the read-only `derivationBaseFor(id)` (a built-in is its own base, a user style uses its recorded entry, an absent entry falls back to the default built-in with one warning — one rule, shared with `duplicate`), merges the source's migrated text over that base with `StyleMerger.merge` (D-72) so the copy is the full resolved document, names it with `StyleCopyNaming.nameFor(sourceName, repository.list() names)` (Q8), allocates a fresh id and issues exactly one `create(..., derivationBaseId = base, activate = false)`. It does not switch: the active style, the single active marker and the one preview card stay where they were, and no modified time is added to `StyleSummary`. The coordinator's result is returned unchanged, so `Saved` carries the fresh id, revision and base, and `Failed`/`Rejected`/`Partial`/`StaleStyle` keep their meaning. A duplicate write failure adds no style and no derivation entry.

**Rename (Q8).** [VERIFIED — source/test] Only user rows offer the affordance; a built-in row has none, and the command layer still proves the refusal because the coordinator's existing built-in rule rejects any rename of a built-in id (the command does not pre-empt it with a second rule). For a user style the command trims the draft, refuses a blank name and a name that equals another style's name case-insensitively (`repository.list()` excluding the style itself) with a typed `Rejected` carrying a `name` issue and never silently disambiguates; otherwise it issues exactly one `coordinator.rename(id, revision observed when the dialog is confirmed, name)`. Identity is the id, the derivation entry is untouched, no modified time is added and `StyleSummary` keeps its fields. The dialog is seeded with the current name, stays open on a refusal with the coordinator's detail and "The name did not change.", and closes only when the rename committed. The active marker and preview follow the renamed style because they read the resolved profile, not a row copy.

[VERIFIED — test] The screen keeps the WP02 contract: one active marker (`selected` plus the visible "Active" label), one preview card, pick is still the only switch, and every new action is a labelled `Role.Button` with a content description ("Duplicate <name>", "Rename <name>"). A failed duplicate shows "Could not duplicate <name>." with the coordinator's detail and states that no style was added and the active style did not change.

## 8. Delete, damaged files and recovery (TODO 5b WP04, D-97/F-41)

[VERIFIED — source] **Delete.** A user style gets a Delete affordance on its row; a built-in row never does, and both the ViewModel (`beginDelete`) and the coordinator refuse a built-in id. Delete is confirm-and-permanent: the dialog names the style, says "This permanently deletes the style file. It cannot be recovered from the app.", offers "Delete style"/"Keep style", and only the confirm issues exactly one `StyleMutationCoordinator.delete(id)`. There is no trash store, no second write path and no Undo entry (Undo is 5d, and `StyleEditorCommandsTest` proves the session count does not change across a delete); the coordinator's typed result is returned unchanged, so a `Failed`/`Partial`/`Rejected` keeps the dialog open with its own detail and never looks applied. Deleting the active style clears the pointer, the existing resolver falls back to the resolved default, and the single preview card names that default with "The deleted style was the active one, so the default style is now in use." — the fallback never looks like an ordinary editable selection.

[VERIFIED — source/test] **Damaged entries.** `StyleRepository.listing()` is the additive read surface next to the unchanged `list()`/`read()`: it returns a sealed `StyleListEntry` where a user file that cannot be read, cannot be decoded or declares another id is a `Damaged(id, path, detail, modifiedAt)` row instead of being skipped. It runs the same text → migrator → decoder path as `list()` — no second decoder or validator — keeps `list()`'s order and rules (first duplicate id wins, a user file shadows the built-in of the same id, a damaged built-in asset stays the D-106 skip with one warning), and carries the file's last modified time (`null` when the file system reports none, and always `null` for a built-in). `detail` is path-qualified: the absolute file path plus the failing JSON path and message. A damaged row is never pickable — the ViewModel refuses the pick before the coordinator — and shows "Needs attention", the detail and only three actions: export raw file, reset to default, delete.

[VERIFIED — source/test] **Recovery commands.** All three live on the same coordinator, under the same one mutex and with the same typed results, and `delete` now shares one private `removeStyleFile` with the recovery delete (pointer snapshot → store delete with the D-113 pre-deletion snapshot → derivation clear), so there is no second pointer, fallback or write path:

- `exportRaw(id)` returns `StyleRawResult` with the exact stored bytes via `StyleRepository.readRaw(id)` — `File.readBytes()`, no migration, decoding or normalization, and the file is untouched. `readText()` is deliberately not this path because it migrates and can reject. A missing file is `NotFound`; a built-in has no stored file. The screen shows the file name and byte count and hands the bytes to the caller; it writes nothing.
- `deleteDamaged(id)` removes a damaged file through the shared removal path with the same confirm dialog and permanent-deletion copy.
- `resetDamagedToDefault(id)` writes the resolved default built-in's content under the damaged style's own id (`copy(id = id)`) and records that default as the D-82 derivation base, in one committed write; a refusal from the writer or a failed derivation record keeps its ordinary typed shape (`Rejected`/`Failed`/`Partial`).

`deleteDamaged` and `resetDamagedToDefault` refuse a valid style (`Rejected`: "use the ordinary command") and an unknown/invalid id keeps its `NotFound`/`Rejected`, so the recovery path can never stand in for the ordinary validated commands, whose own behavior is unchanged.

[VERIFIED — test] A damaged file is not in `list()`, `read()` still reports its typed rejection, and `listing()` surfaces it with its path. Exporting returns byte-identical content and leaves the file as it was; resetting writes once and makes the id readable again under the default's content; deleting a damaged active id clears the pointer and the default applies with "The selected style needs attention, so the default style is in use for now." until the user picks another style. Every affordance is a labelled `Role.Button` with a content description ("Delete <name>", "Export the raw file for <name>", "Reset <name> to the default style"); the D-114 back chain and the route-scoped session are unchanged.
